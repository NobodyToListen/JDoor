Product principles 01 / 06

Consent is not a prompt. It is the product boundary.

Remote assistance becomes safer when the host can see who is asking, decide what is allowed and end access without negotiation.

01

Approval stays local

The host sees the helper’s device name, network address and verification code before accepting the connection.

02

Viewing comes first

An approved session shares the primary display but ignores mouse and keyboard input until the host enables control.

03

Permission is reversible

Control is scoped to one session. The host can revoke it instantly, releasing every tracked key and pointer state.

04

Nothing hides

There is no unattended access, persistence, remote shell, stealth mode or background foothold.

Session flow 02 / 06

Five deliberate steps. No invisible hand-off.

Pairing combines cryptographic checks with a human decision. Neither one substitutes for the other.

01
HOST / CREATE

Create an ephemeral identity

The host creates a fresh P-256 certificate, an exact SHA-256 fingerprint and a random 128-bit token that expires after 10 minutes.

02
PEOPLE / SHARE

Send one complete link

The host shares the one-time jdoor:// pairing link through a trusted, out-of-band channel with the intended helper.

03
CLIENT / VERIFY

Pin the exact endpoint

The helper’s client checks the advertised host and the exact certificate fingerprint before sending the single-use token inside TLS 1.2/1.3.

04
HOST / APPROVE

Compare, then approve

Both people compare the visible code. The host reviews the request and approves it on the machine being shared.

05
SESSION / VIEW

Start view-only

Frames begin only after approval. Remote input stays disabled unless the host explicitly enables it for that session.

This website does not start or join remote sessions. It explains the desktop product and links to inspectable source and documentation.

Trust model 03 / 06

Pairing proves the endpoint. The host decides the person.

JDoor does not outsource trust to an account service. It binds one short-lived link to one TLS identity, then asks the host for visible consent.

01

Encrypted transport

TLS 1.2/1.3 protects the direct session from passive network capture.

02

Exact certificate pin

The fingerprint in the pairing link must match the certificate presented by the advertised host.

03

Bounded protocol

Version, type, size, range and UTF-8 checks reject malformed messages before they become unbounded work.

04

One active viewer

Pending handshakes, setup time, frame sizes, queues and session state all have explicit limits.

Privacy and audit 04 / 06

Local by design. Accountable without recording the session.

Screen frames and input events travel only between the approved desktop endpoints. The product has no telemetry, analytics, crash upload, account service or public relay.

The host keeps a bounded record of security events, not a copy of what happened on screen.

STORED LOCALLY

Timestamp, event type, remote network address and a short lifecycle description.

NEVER LOGGED

Pairing tokens, private keys, screen pixels, typed content and raw input events.

BOUNDED

Each daily JSONL file is capped at 5 MiB, with 30 days of application-managed retention.

Deliberate limits 05 / 06

A smaller capability surface is part of the security model.

JDoor is built for one host and one trusted helper on a local network. It does not pretend to be an internet-facing remote-management platform.

IN SCOPE

Authorized, visible support

  • +Direct LAN connection
  • +One approved viewer
  • +Primary-display sharing
  • +Optional, revocable input
  • +Local, bounded audit events
INTENTIONALLY ABSENT

No hidden administration layer

  • −Unattended access or persistence
  • −Remote shell or privilege escalation
  • −File or clipboard transfer
  • −Webcam, microphone or stealth capture
  • −Public relay, accounts or NAT traversal

Network boundary: do not expose the default port directly to the internet. JDoor currently assumes a trusted local network and an out-of-band channel for the complete pairing link.
